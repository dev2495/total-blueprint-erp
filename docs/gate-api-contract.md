# Gate API (all paths under `/api/gate/`)

The application is registered as `apps.gate`. WATCHMAN receives `gate.log` only and requires an explicit `GateAssignment(user, plant)`; an empty assignment fails closed. Owner-only history, audit and corrections are enforced in the application independently of STRICT_RBAC. A delegated `gate.reports` grants only sanitized aggregates/CSV.

## Mobile watchman

- `GET masters/?plant=<uuid>&q=<text>`: `{plants:[{id,name,code}], parties:[{kind:"VENDOR"|"CUSTOMER",id,name,code}], products:[{kind:"MATERIAL"|"PRODUCT"|"TRADING"|"CONSUMABLE",id,name,code,uom}], units:[<master-derived unit codes>], purposes:[...]}`. Query search is optional, cap 100 per master family; selected masters validated active server-side. Global customer/material masters have no plant field; document matches are plant scoped.
- `GET match/?plant=<uuid>&direction=INWARD|OUTWARD&invoice_number=<text>&party_kind=VENDOR|CUSTOMER&party_id=<uuid>`: `{status:"MATCHED"|"AMBIGUOUS"|"UNMATCHED",candidates:[{kind,id,reference,party_kind,party_id,party_name,invoice_date,vehicle_number,lines:[{product_kind,product_id,product_name,quantity,uom,amount}],amount,amount_basis}]}`. INWARD matches supplier invoices in GRN/trading receipts. OUTWARD matches confirmed/dispatched CustomerDispatch invoice_no/code, dispatched/invoiced TradeOrder invoice_no/code and legacy challan dc_no. Outgoing source records have no invoice-date field, so it stays unknown rather than substituting order/dispatch dates. Amount basis is disclosed per reference; sales estimates are not accounting invoice totals. No stock/accounting writes.
- `POST goods/`: `{client_token:<UUID>,plant:<uuid>,direction,invoice_number,vehicle_number,party_kind,party_id,invoice_date?:"YYYY-MM-DD",lines?:[{product_kind,product_id,quantity,uom,amount?:decimal}],document_kind?:"GRN"|"TRADING_RECEIPT"|"DISPATCH"|"CHALLAN"|"TRADE",document_id?:uuid,notes?:text}`. Invoice and vehicle typed. A selected ERP match supplies party/lines/date/amount; optional observed lines produce explicit discrepancy. An unmatched movement requires a selected active master party and at least one active master product with observed positive quantity; amount can be unknown/null. Returns stored goods object plus `replayed`. Duplicate invoice+party+direction+plant+Indian April–March financial year is rejected (invoice date when known, otherwise physical logged business day); corrections recompute this namespace; token reuse with changed payload returns 409. No PUT/PATCH/DELETE.
- `GET goods/`: paginated `{count,next,previous,results}`. WATCHMAN receives today's scoped movement receipts only. Owner receives full history and filters `plant,direction,search,date_from,date_to,reconciliation_status`.
- `GET visitors/?plant=<uuid>&status=INSIDE`: watchman exit queue, pagination/search, default INSIDE only; other explicit status filters are denied. INSIDE is ordered oldest entry_at, submitted_at then id across all server pages. Fields `{id,plant,plant_name,name,mobile,purpose,company,source,status,submitted_at,entry_at,exit_at,government_id_masked,has_selfie,selfie_url}`.
- Watchman cannot create visitor entries, check in, or cancel registrations. Visitors scan the factory QR and submit their own details; submission immediately records entry.
- `POST visitors/<uuid>/check-out/`: `{client_token:<UUID>}`. Only INSIDE -> EXITED, using server time and a serialized row lock. Same token+payload returns original result; changed payload conflicts. A second exit with another token returns 409.
- `GET visitors/<uuid>/selfie/`: authenticated image/jpeg, private/no-store. WATCHMAN only INSIDE visitors at assigned plants. Owner full history.
- `GET summary/?plant=<uuid>`: today's inward/outward plus current pending/inside/overdue visitor counts; historical summaries owner-only.

## Public visitor self-registration

- `GET public/config/?gate_token=<UUID>`: `{company_name:"Total Poly Print",plant_name,plant_code,purposes:[...],privacy_note,government_id_enabled}`. Only the single public gate label is exposed; no plant IDs or plant enumeration. Invalid/unavailable token is 404. QR target `/visit/<gate_token>`.
- `POST public/visitors/`: JSON or multipart `{client_token:<UUID>,gate_token:<UUID>,name,mobile,purpose,company?:text,government_id_type?:"AADHAAR"|"PAN"|"OTHER",government_id_number?:text,consent:true,selfie?:file}`. JPEG/PNG/WebP up to 3 MB, sanitized and resized server-side. Govt ID optional; encrypted only with GATE_ID_ENCRYPTION_KEY, otherwise 503 when supplied (omitted IDs work). Submission creates INSIDE with submitted_at, consent_at and entry_at set to the same server timestamp; entry_by remains null. Returns only `{receipt_id,status:"INSIDE",entry_at:<server ISO timestamp>,message:"Entry recorded. Please ask the watchman to confirm your exit when leaving.",replayed}`. The receipt entry_at is the exact persisted server timestamp and stays identical on retry. Immutable VISITOR_REGISTERED and VISITOR_ENTERED events are appended atomically once; a retry preserves the receipt, entry timestamp and audit count. No public list/detail/status/photo read.

## Owner and reports

- Owner `GET visitors/` supports all statuses and dates; unfiltered history remains newest first. Legacy/recovery PENDING queues sort by submitted_at then id. Existing PENDING rows are preserved. Owner-only `POST visitors/` accepts the public payload with `plant:<uuid>` in place of gate_token and creates PENDING with source OWNER for recovery. Owner-only `POST visitors/<uuid>/check-in/` admits PENDING; `cancel/` closes PENDING without entry timestamps and requires reason preset `Visitor left`, `Duplicate / mistaken registration`, `Entry declined`, or `Visit cancelled`. Watchman cannot use these recovery actions.
- `GET goods/<uuid>/`: owner complete detail; `POST goods/<uuid>/reconcile/`: `{client_token,reason,document_kind,document_id}`. Reference must satisfy same plant/direction/party. `POST goods/<uuid>/correct/`: `{client_token,reason,vehicle_number?,invoice_number?,invoice_date?,notes?,lines?}`; mandatory reason and immutable before/after event. Does not rewrite source ERP transactions.
- `GET audit/?object_id=<uuid>&plant=<uuid>`: owner immutable paginated events, actor, server timestamp, reason, before/after safe snapshots; no raw ID/selfie data.
- `GET reports/?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&plant=<uuid>`: owner or `gate.reports`, sanitized aggregates, no personal data. `GET reports/csv/` exports sanitized goods register (CSV formula neutralized). Max date range 366 days.
- Python integration: `apps.gate.services.summary_for_period(start_date,end_date,plant_ids=None)` returns `goods_total,inward,outward,unmatched,discrepancies,pending_visitors,inside_visitors,visitor_entries,visitor_exits,overdue_visitors,amount_by_direction,quantity_by_uom`. Current visitor status is clearly separate from period entry/exit counts.

Errors are standard DRF JSON: 400 validation, 403 permission/plant, 404 scoped unknown object, 409 stale state/duplicate or token payload conflict, 429 public rate limit, 503 optional ID encryption unconfigured. Always retain the same client token during retries and generate a new token only for a new human action.

QR: owner `GET qr/?plant=<uuid>` returns `{plant_name,plant_code,gate_token,public_url,svg_url}`. `GET qr/<plant uuid>/svg/` returns real SVG QR with HIGH error correction and a four-module quiet zone. The poster may add a bounded TPP center badge only after an independent scanner decodes the exact registration URI at mobile and print sizes; preserve the quiet zone, use the server QR modules, and do not redraw or arbitrarily mask modules. Existing plant links are seeded in migration. New plants automatically receive a QR link during their normal creation flow; updates preserve existing tokens. `manage.py configure_gate_links` remains an idempotent bulk recovery tool for existing/imported plants, never needed during normal owner creation. GATE_PUBLIC_ORIGIN supplies public origin; GATE_TIME_ZONE defaults to Asia/Kolkata. Optional ID encryption failure includes `code=GATE_ID_STORAGE_UNAVAILABLE`, guarantees no visitor commit. Retry using a new token after removing the refused ID.

Duplicate invoice identity uses the Indian financial year starting in April. March 2026 is FY2025, April 2026 is FY2026. The gate-only invoice_year stores the FY starting year. ERP document identity is separately unique per plant/direction even if an observed invoice date changes.

Legacy DRAFT delivery challans may be selected for a physical observation, but save always flags DISCREPANCY with an explicit unposted-dispatch warning. The gate does not post that challan. Owner reconciliation can refresh the reference after the normal ERP dispatch workflow posts it.
