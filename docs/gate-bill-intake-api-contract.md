# Camera-only inward bill intake — final API contract

All bill paths are under `/api/gate/inward-bills/`. Authentication and normal cookie CSRF apply; bill images are never public. No OCR, AI extraction, external provider, email or SMS is involved. Visitor watchman exit flow and outward goods logging remain unchanged. Watchman manual `POST /api/gate/goods/` with direction INWARD is refused; existing inward history is preserved.

## Watchman arrival

- `POST /api/gate/inward-bills/`, multipart: `client_token` UUID, `plant` UUID, repeated `images` files in page order. No invoice, vehicle, vendor, product, quantity or amount input. Scope is the watchman's assigned gates (master accounts all plants). Exactly 1–6 JPEG/PNG/WebP images, maximum 10 MiB per input, 40 million pixels per image, minimum dimensions 320×320. Server rotates using EXIF, removes metadata, normalizes readable JPEG up to 2400 px on the long edge, maximum 2 MiB per stored page. HEIC/PDF/SVG/non-image content is refused with a clear format error. Upload all pages together; one invalid page rejects the entire arrival.
- Response 201: `{id,plant,plant_name,arrival_at,status:"PENDING_GRN",created_by_name,page_count,pages:[{id,page_number,width,height,byte_size,image_url}],review_data:{},receipt_refs:[],resolution_reason:"",resolved_at:null,duplicate_warning:{possible_duplicate:boolean,bill_ids:[]},replayed:false}`. Arrival time is server time. Watchman responses retain empty review_data/receipt_refs/resolution fields and no other bill IDs; inventory reviewers receive those allowed fields. Current role redaction is applied again on cached retries. Same token and same ordered normalized image content returns the original response with `replayed:true`; changed payload returns 409. A new token with identical content records an arrival and warns inventory, allowing legitimate repeated paperwork. One arrival/audit/notification set per successful token. Stock is unchanged.
- `GET /api/gate/inward-bills/?plant=<uuid>` and `GET .../<uuid>/`: watchman sees only their own arrivals from today at assigned gates. Master/review users see their authorized inventory scope. Paginated `{count,next,previous,results}`, page_size 1–100. Review users filter `status=PENDING_GRN|PARTIAL_GRN|RECEIPTED|VOID`, `search`, `date_from`, `date_to`; PENDING_GRN is oldest arrival first with id tie-breaker. Default review queue contains PENDING_GRN and PARTIAL_GRN; `status=ALL` gives history. Watchman status/date history filters are denied.
- `GET .../<bill uuid>/pages/<page uuid>/`: authenticated JPEG with private/no-store and nosniff. Same scope as detail; no image bytes appear in list JSON or audit/notification payloads.

## Inventory review and receipt

`gate.bill.review` requires shared actual inventory receipt eligibility and its existing plant scope; actual/effective WATCHMAN cannot review, even with stale flags. Masters retain full rights. Current inventory receipt users have global authorized plant scope as in the existing ERP; no new assignment requirement is introduced.

- `POST .../<uuid>/review/`: `{client_token,vendor_id?:uuid,invoice_number?:text,invoice_date?:YYYY-MM-DD,vehicle_number?:text,purchase_order_id?:uuid,notes?:text}`. Only human inventory input while PENDING_GRN or PARTIAL_GRN; master vendor must be active, optional PO must match plant/vendor. Stores validated prefill while PENDING_GRN or PARTIAL_GRN; audit retains allowed field changes. This does not create stock or infer data from images.
- `GET .../<uuid>/receipt-candidates/?search=<invoice or reference>&vendor_id=<uuid>`: `{results:[{kind:"BULK"|"PACKAGING"|"ROLL"|"PO_RECEIPT"|"TRADING",id,reference,invoice_number,vendor_id,vendor_name,plant,received_at,quantity,quantities_by_uom,uom,quality_status}],matching_is_manual:true}`. Mixed-unit PO receipts return quantity:null, uom:"MIXED", and quantities_by_uom without adding unlike units. Only positive received, non-rejected, same-plant documents within 24 hours before arrival or after it, excluding sources already linked to another bill. Bounded to 100 candidates; explicit human selection and confirmation is required. These are receipt references, not stock balances; consumed stock can still have a valid original receipt.
- Existing GRN create endpoints remain the accounting source of truth. Add `inward_bill_id:<uuid>` and `client_token:<UUID>` to the existing JSON request for `/api/inventory/grn/create/` (BULK/ROLL/PACKAGING) or `/api/procurement/purchase-order-receipts/` (PO header/lines) and `/api/procurement/trading-good-receipts/` (TRADING). Bill-linked posting requires a nonblank vendor_invoice_no (the manually entered invoice/bill reference); omit Idempotency-Key or make it equal client_token. All three posting APIs accept `bill_complete:boolean` default false. Hook verifies reviewer and every receiving location/PO plant, locks the bill before the existing posting service, and atomically records the created references and PARTIAL_GRN status; only explicit bill_complete=true confirms all bill lines are received and sets RECEIPTED. Response retains original GRN fields and adds `inward_bill:{id,status,resolved_at}` plus `replayed`. PENDING_GRN/PARTIAL_GRN may accept several class/PO/trading receipts; partial bills remain in the inventory queue. A same-token replay returns the same posting response without additional stock. A first-attempt collision with an existing ERP posting token returns 409; existing receipt matching requires explicit link-receipts selection. Changed payload, another posting token on a resolved bill, cross-plant receipt or rejected quality is refused. A failed GRN rolls back both stock and bill linkage. Existing receipt endpoints without inward_bill_id retain their behavior.
- `POST .../<uuid>/link-receipts/`: `{client_token,receipt_refs:[{kind,id}],reason:<5–500 chars>,bill_complete?:boolean}` links already-posted receipts using the same same-plant/time/quality checks. All selected references must share a vendor; optional reviewed vendor/invoice must agree. One source can belong to only one bill; a PO header and its physical BULK/ROLL/PACKAGING rows are overlapping aliases and cannot be linked twice, even within the same request. Children of rejected PO headers are excluded too. Requires PENDING_GRN or PARTIAL_GRN; appends references atomically and defaults to PARTIAL_GRN. Explicit bill_complete=true confirms all lines received and closes RECEIPTED. Does not post stock.
- `POST .../<uuid>/complete/`: `{client_token,reason:<5–500 chars>}` explicitly confirms all bill lines are received after one or more posted references; transitions PARTIAL_GRN to RECEIPTED without posting stock. An empty bill cannot be completed.
- `POST .../<uuid>/void/`: `{client_token,reason:<5–500 chars>,resolution_code:"DUPLICATE"|"NON_STOCK"|"UNREADABLE"|"CANCELLED",duplicate_of?:uuid}`. Only reviewer; PENDING_GRN -> VOID, permanent explained audit, no deleting images or fake receipt. DUPLICATE requires another same-plant bill. Use NON_STOCK for equipment/service paperwork that does not belong in the stock GRN workflow.

Receipt links are `{kind,id,reference,invoice_number,vendor_id,vendor_name,received_at,quantity,quantities_by_uom,uom,quality_status}`. The arrival, review and resolution events use immutable GateAuditEvent history (including its SQL update/delete guard). Arrival notifications are immediate user-targeted in-app records inside the same transaction and contain only bill/plant identifiers, arrival time, pending status and a queue link. No commercial image contents enter a notification.

Errors: 400 invalid image/master/location/receipt/reason, 403 unauthorized role/scope/manual inward bypass, 404 scoped unknown bill/page, 409 retry payload conflict or resolved/already-linked receipt. All mutations require a UUID client_token retained across uncertain retries. `review`, `link-receipts`, `complete`, `void` return the bill object plus replayed. There are no PUT/PATCH/DELETE bill/page endpoints.

Frontend: watchman inward is a camera/upload page with ordered preview/removal before submission and server arrival receipt; outward and visitor exit retain their current flows. Inventory queue links into existing GRN forms with bill images alongside editable master-backed fields; retain inward_bill_id and the posting client_token through retries. A posted GRN remains PARTIAL_GRN by default so mixed classes/multiple receipts cannot hide unfinished bill lines. Inventory explicitly confirms all received using bill_complete=true on the last posting/link operation or complete afterward. Existing-GRN selection uses link-receipts; final confirmation uses complete. No stock action runs in final confirmation. Duplicate/non-stock resolution is inventory-only and explained.
